## 一、产品团队实际在解决什么

WorkBuddy的实践给出了一个更接近产品现场的视角：模型只是无状态的推理引擎，产品需要在外部组织上下文、能力、权限、验证和长期状态。产品团队关心的不是单独把某个Retriever指标做高，而是Agent能否稳定、可控地完成任务。

|产品问题|WorkBuddy采用的思路|需要观察什么|
|---|---|---|
|能力太多，不能全部放进上下文|意图识别、名称和简介优先、完整Schema和Skill按需加载|上下文长度、能力选错率、任务成功率|
|动态信息和长期规则混在一起|稳定内容放前部，动态内容按需追加|Prompt Cache、更新及时性|
|历史信息持续影响未来任务|Memory保存事实，Skill保存可评审的做事方法|错误记忆、过期流程、作用域|
|模型会执行真实操作|权限、Sandbox、Approval、验证和审计放在模型外|越权、失败恢复、可追溯性|
|复杂任务需要持续推进|Task、Sub-Agent、反馈、状态和停止条件|任务完成、成本、恢复能力|
|一组能力需要安装和分发|Plugin组合MCP、Skill、Rule、Hook和模板|安装范围、更新、兼容与治理|

这说明**能力发现和渐进式加载已经是真实产品需求**，但还不能直接推出“运行时自动检索并安装Plugin”也是刚需。当前更需要确认的是：Plugin由人预装还是由系统动态选择；运行时检索发生在Plugin、Skill还是Tool层；产品最主要的问题是上下文成本、能力选错、冷启动、权限还是任务完成率。

## 二、能力的四种载体

智能体需要的能力并不只有Tool。Document提供信息，Skill提供程序性知识，Tool提供原子操作，Plugin将多种能力和运行时资源组织在一起。四者可以同时存在，也可以相互包含。

|阶段|检索对象|回答的问题|主要风险|
|---|---|---|---|
|文档检索|事实与证据|需要知道什么？|错误证据|
|Skill检索|流程与脚本|应该怎么做？|流程或组合错误|
|Tool检索|已暴露接口|下一步调用什么？|接口、参数或顺序错误|
|Plugin检索|运行时组件|应该具备什么能力？|依赖、权限和状态问题|

这不是严格的历史顺序，也不是后一层淘汰前一层。Plugin可以提供Tool和Skill，Tool负责执行原子操作，Skill负责描述程序性知识。随着智能体开始处理更完整的任务，系统需要管理的对象从“给模型看什么”逐渐扩展到“给模型什么能力、这些能力如何配合、执行后如何收尾”。

## 三、检索为什么是核心入口

当Document、Skill、Tool和Plugin的数量不断增加时，把全部内容和接口默认交给模型既昂贵，也容易引入无关能力。检索负责从大目录中缩小范围，决定后续推理、组合和执行建立在什么能力之上。

我们此前在R3-Skill中研究了Skill Retrieval。文档通常可以分别判断相关性，但复杂任务需要多个Skill协作；每个Skill单独相关，不代表它们在当前需求下可以自然组合。因此，R3-Skill将问题拆成两部分：

- **单体相关性：** 某个Skill是否与query相关；
- **查询条件兼容性：** 多个Skill在当前query下是否应该共同出现。

我们保留了数据生成过程中原本会被丢弃的拒绝样本，用它训练和评测多Skill路由。这个工作仍然主要发生在**模型上下文层：** 检索器决定向模型加载哪些程序性说明。

Tool Retrieval更接近执行层，研究如何从大量接口中选择工具、补齐依赖并规划顺序。现有工作已经覆盖平面检索、依赖图、任务分解、动态检索和MCP多工具编排，但多数工作有一个共同前提：**Tool所属的服务已经安装、连接并暴露给Agent。**

## 五、能力组织为什么会走到Plugin

Plugin不是更长的Tool描述。一个插件可能同时：

- 注册多个Tools；
- 提供或依赖Services；
- 加载Skills和Prompt；
- 启动进程、连接和后台任务；
- 管理Memory、Credentials和Policy；
- 替换模型、沙箱或Agent Loop实现。

因此，Tool Retrieval回答的是“现有能力中调用什么”，Plugin Retrieval要回答的是“哪些能力应该进入当前运行时”。

|Tool检索|Plugin检索|
|---|---|
|输入：query+Tool描述|输入：query+环境+Harness状态|
|输出：Top-K Tool|输出：配置增量+依赖图|
|Tool已经可用|处理安装、绑定、激活与退出|
|关注调用正确|同时关注安全、成本与状态|

## 六、从发现能力到完成任务

一条完整链路至少包括：**发现候选能力 → 选择相关能力 → 补齐依赖和配置 → 执行任务 → 记录反馈 → 退出并回收状态。**

用户要求：**检索论文、下载PDF、建立索引并生成报告。**

- **允许外网且有API密钥：** 可以选择远程学术搜索和远程Embedding插件；
- **禁止外网但有本地论文镜像和GPU：** 应切换到本地检索和本地模型；
- **文件系统只读：** 下载和建立索引不可执行，应选择只读分析方案或明确拒绝；
- **已有向量库Provider：** 应优先复用，而不是重复安装另一套存储。

同一个query在不同环境中可能对应不同插件方案。因此，结果不应只是固定Top-K，而应说明：**增加或移除哪些插件、依赖绑定到哪个Provider、采用什么配置和权限，以及任务完成后如何退出。**

## 七、目前需要验证的问题

1. **环境是否真的改变答案？** 如果去掉环境信息仍能得到相同方案，环境条件插件检索的必要性就很弱。
2. **是否真的需要学习式组合？** 依赖补全、版本检查和Provider选择可能由规则或约束求解器完成，模型或许只需负责语义召回。
3. **真实插件是否存在可用契约？** 公开生态能否稳定提供描述、配置、依赖、权限和生命周期信息，仍需统计。
4. **能否可靠评测？** 除了召回率，还要检查配置可行性、任务完成、权限违规、资源泄漏和卸载后的状态恢复。

这些问题应当允许否定答案。早期实验的目的不是证明方案正确，而是判断问题是否真实、边界在哪里，以及学习方法相对规则系统是否有必要。

## 八、后续工作路线

|步骤|要回答的问题|预期产出|
|---|---|---|
|产品访谈|Plugin由谁安装？能力检索在哪一层？当前最影响体验的问题是什么？|真实场景、失败案例和指标口径|
|数据确认|是否能获得query、候选能力、实际选择、缓存和执行结果？|可用字段、隐私边界和样本规模|
|问题收敛|需要优化的是Skill/Tool选择、Plugin组织，还是整体能力路由？|明确任务定义和不做的范围|
|小规模验证|规则、现有Retriever和动态方案分别表现如何？|是否值得继续投入的证据|
|扩大建设|问题成立后再构建数据、训练模型和接入业务|可部署方案与线上评测|

需要优先向产品团队确认：

1. Plugin目前由人安装，还是会根据任务自动加载；
2. Tool Retrieval是在全局能力库中进行，还是只在已安装Plugin内部进行；
3. 动态Tool和Skill被放在请求的什么位置，多久变化一次；
4. 是否已经统计Tool数量、Cache Hit、TTFT、调用失败和任务完成；
5. 业务目前最明显的问题是能力选错、上下文成本、冷启动、权限，还是任务成功率。

如果可以获得真实Trace，优先记录：

```text
query / intent
候选与选中的Skill、Tool、Plugin
当前用户、项目和环境作用域
System Prompt与Tool Schema摘要
inputTokens / cacheReadTokens / TTFT
Tool执行结果与任务完成情况
```

确认业务问题和数据以后，再进入“语义召回 → 组合验证 → 隔离执行 → 反馈学习”。如果真实产品只需要预装Plugin后的Tool/Skill检索，就不应为了形式完整强行把问题扩大成动态Plugin Retrieval。
